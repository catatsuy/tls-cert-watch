# tls-cert-watch

外部からTLS 1.3で接続し、実際に配信されるRSA・ECDSA証明書を個別に検査する小さなGo CLIです。Let's Encryptの6日間証明書など、短命証明書の更新失敗の検出を目的としています。この外形監視自体は状態の保存・通知の重複排除・外部APIを使用しません。独立したCTログ監視は後述します。

## 監視の仕組み

ホストと鍵種別ごとに、別プロセスの `openssl s_client` で新しいハンドシェイクを行います。SNIを明示し、`-tls1_3 -sigalgs` で提示する署名アルゴリズムを制限します。

- RSA: `rsa_pss_rsae_sha256/384/512` と `rsa_pss_pss_sha256/384/512`
- ECDSA: `ecdsa_secp256r1_sha256`、`ecdsa_secp384r1_sha384`、`ecdsa_secp521r1_sha512`

通常のTLS接続ではクライアントの提示内容によって選ばれる証明書が変わり、一方の証明書の更新失敗を見逃す場合があります。そのためRSAとECDSAを独立して取得します。ECDSAはP-256に限定していません。Go標準の `crypto/tls` はクライアントの署名アルゴリズムを自由に指定できないため、取得にはOpenSSLを使用します。

OpenSSLの終了コード、TLS 1.3の接続成立と暗号スイート、`Verify return code` を確認します。検証失敗時にも証明書を取得するため、`-verify_return_error` は付けず、検証結果が非ゼロ・欠落なら必ず異常とします。終了コード0やPEMの存在だけでは成功と判定しません。標準入力をEOFにして終了し、DNS解決・接続・ハンドシェイクを含むプロセス全体にタイムアウトを設定します。

`-showcerts` のPEMをGoの `crypto/x509` で解析し、公開鍵アルゴリズム、ホスト名、信頼チェーン、サーバー認証用途、有効期間を再検証します。公開鍵アルゴリズムは証明書自体の署名アルゴリズムと区別します。通常はOSの信頼ストアを使い、`-ca-file` 指定時はOpenSSLにそのCAファイルを渡し、Goでは指定CAだけを信頼します。中間証明書はサーバーが配信したチェーンを使用します。

検査失敗後も次の鍵種別・ホストへ進みます。正常・異常のどちらも、ホスト・ポート・要求した鍵種別・実際の公開鍵種別・NotBefore・有効期限・残り時間をログに出します。取得できなかった情報は「不明」と表示します。検証失敗時も取得できた証明書情報を残します。

## 設定

`targets.json` には `catatsuy.org`、`www.catatsuy.org`、`blog.catatsuy.org`、`matw.co` を登録し、各ホストのRSA・ECDSAを検査します。対象を変更する場合は、次の形式で編集してください。

```json
[
  {
    "host": "www.example.com",
    "key_types": ["RSA", "ECDSA"]
  },
  {
    "host": "other.example.com",
    "port": 8443,
    "key_types": ["ECDSA"]
  }
]
```

`host` はスキームやポートを含まないホスト名またはIPアドレスです。国際化ドメインはASCIIのPunycode表記を使ってください。`port` の省略・0は443です。`key_types` は必須で、大文字の `RSA` / `ECDSA` を重複なく指定します。両方を配信するサイトには必ず両方を指定してください。片方しか取得できなくても異常です。空設定や未知のフィールドも設定エラーにします。

## 判定基準

| 有効期限までの残り時間 | 判定 |
| --- | --- |
| 48時間以上 | 正常 |
| 24時間以上48時間未満 | 警告 |
| 0時間超24時間未満 | 緊急 |
| 0時間以下 | 異常（期限切れ） |

残り時間は各検査の実行時刻と `NotAfter` の差で判断し、日数への丸めは行いません。48時間ちょうどは正常、24時間ちょうどは警告です。未発効・不正な有効期間、ホスト名・チェーン・鍵種別の不一致、証明書欠落、接続失敗、タイムアウト、OpenSSLの実行失敗も異常です。証明書の検証に失敗した場合は、期限の判定にかかわらず異常です。

警告・緊急・異常はすべてSlack通知と終了コード1の対象です。全検査が正常なら通知せず0で終了します。

## ローカル実行

Go 1.24以上、TLS 1.3対応OpenSSL（OpenSSL 3推奨）、信頼できるCAストアを用意します。Goの外部モジュール依存はありません。

```sh
go build -o tls-cert-watch .

# Slack通知なしで検査する（異常時の終了コードは1）
./tls-cert-watch -config targets.json -no-slack

# macOSの標準opensslはLibreSSLの場合があるため、Homebrew版を明示できる
./tls-cert-watch -config targets.json -no-slack \
  -openssl /opt/homebrew/opt/openssl@3/bin/openssl
```

Slack通知はGoの標準ライブラリからSlackの `chat.postMessage` APIを直接呼び出します。追加の通知CLIは不要です。既存のSecrets・環境変数名はそのまま使います。

```sh
export NOTIFY_SLACK_TOKEN='...'
export NOTIFY_SLACK_CHANNEL_ID='...'
./tls-cert-watch -config targets.json
```

主なオプション（全体は `-help`）：

| オプション | 既定値 | 用途 |
| --- | --- | --- |
| `-config` | `targets.json` | 設定ファイル |
| `-openssl` | `openssl` | OpenSSLの実行ファイル |
| `-timeout` | `20s` | 1検査のタイムアウト |
| `-notify-timeout` | `1m` | 集約通知のタイムアウト |
| `-ca-file` | 未指定 | 独自CAのPEMファイル |
| `-no-slack` | false | ローカル検査用に通知を省略 |

異常がある場合だけ、全対象の異常を `@channel` メンション付きの1メッセージにまとめて投稿します。正常な検査結果は実行ログに記録します。通知例：

```text
@channel
TLS証明書の監視で問題を検出しました
検査 8件中 2件に問題があります。
証明書の自動更新・配信設定を確認してください。

⚠️ 警告 — catatsuy.org:443 / RSA
有効期限: 2026-11-04 12:00:00 UTC
残り時間: 36時間20分0秒
問題:
• 有効期限まで48時間未満

🚨 異常 — blog.catatsuy.org:443 / ECDSA
有効期限: 不明（証明書を取得できませんでした）
残り時間: 不明
問題:
• OpenSSL実行/TLS接続失敗: context deadline exceeded
• TLS 1.3ハンドシェイク成功を確認できない
• 証明書が取得できない
```

有効期限はUTCで表示し、期限切れの場合は経過時間を表示します。OpenSSLの生の診断出力は実行ログに残します。通知中の長いエラーは省略表示し、Slackの文字数制限を超える多数の異常は省略件数を明示します。全件の詳細は実行ログで確認できます。設定読み込み失敗など、監視を開始できない場合も `@channel` 付きで通知します。認証情報やAPIレスポンス本文はログに出しません。

通知完了を待ってから異常終了します。Secrets未設定、HTTPエラー、Slack APIの `ok: false`、通知のタイムアウトも終了コード1です。正常時にはSlack認証情報は不要です。状態を持たないため、異常が続く限り実行ごとにメンション付きで通知します。

## GitHub Actions

1. `targets.json` を実際の監視対象に更新してデフォルトブランチへ反映します。
2. Slack AppのBot Tokenに `chat:write` を付与し、ワークスペースへインストールして投稿先チャンネルへ招待します。既存のAppに `chat:write` を追加した場合は、Appを再インストールして権限を反映してください。ファイル投稿用の `files:write` は不要です（他のツールでも使っているAppでは、そのツールの必要権限を残してください）。
3. リポジトリの **Settings → Secrets and variables → Actions** に次のSecretsを登録します。

| Secret | 内容 |
| --- | --- |
| `NOTIFY_SLACK_TOKEN` | Slack Bot Token |
| `NOTIFY_SLACK_CHANNEL_ID` | 投稿先チャンネルのID（名前ではない） |

`.github/workflows/watch.yml` はUbuntu runnerで、UTCの00:17 / 03:17 / 06:17 / 09:17 / 12:17 / 15:17 / 18:17 / 21:17（日本時間も3時間ごとの17分）に実行します。Actionsタブの **TLS certificate watch → Run workflow** で手動実行できます。

OpenSSLとCA証明書をインストールし、Goから検査とSlack通知を実行します。権限は `contents: read` だけで、GitHubへの書き込みや状態用ブランチ、DB、Heartbeat、他の監視サービスは不要です。ジョブ全体のタイムアウトは15分、通常の1検査は20秒です。対象を大量に追加する場合は検査数とタイムアウトの合計がジョブ上限内に収まるよう調整してください。ジョブ上限による強制終了やrunner/ツール準備自体の障害では、CLIからのSlack通知まで到達できない場合があります。

GitHub Actionsの定期実行には遅延や実行漏れの可能性があります。定期実行はデフォルトブランチ上で動作し、公開リポジトリは長期間の操作がないとスケジュールが無効になる場合もあります。Actionsの実行履歴とスケジュールの有効状態を定期的に確認してください。厳密な3時間間隔の実行を保証する仕組みではありません。

通知方式は [rss-curator](https://github.com/catatsuy/rss-curator) を参考にしています。`@channel` はSlackの [メンション記法](https://docs.slack.dev/messaging/formatting-message-text/#special-mentions) を使用します。実際の通知はSlack側の権限・チャンネルや受信者の通知設定にも従います。

## 開発・テスト

```sh
go test ./...
go vet ./...

# 別のOpenSSLで統合テストする場合
TEST_OPENSSL=/opt/homebrew/opt/openssl@3/bin/openssl go test ./...
```

単体テストでは証明書とCAをその場で生成し、OpenSSL出力を模擬します。RSA/ECDSAの正常・片方だけの期限切れ・取得失敗、鍵種別・ホスト名・チェーンの不一致、未発効、48時間/24時間境界、実行・接続失敗、複数ホストの部分失敗、通知の集約と失敗を検証します。

統合テストではループバックのTLS 1.3サーバーがClientHelloに応じて証明書を出し分け、実際のOpenSSLでRSAとECDSA（P-256 / P-384 / P-521）を別々に取得して検証します。SNI、接続拒否、応答しないTCPサーバーに対するタイムアウトも確認します。外部ネットワークやSlackは呼びません。対応するOpenSSLが未インストールの場合は統合テストをスキップします。macOSでは標準LibreSSLの代わりにHomebrewのOpenSSL 3も探します。ループバックへのbindが許可された環境で実行してください。CIではOpenSSLがあるUbuntu runnerで全テストを実行します。

## CTログの新規発行監視

期限監視とは独立した `CT certificate watch` を追加しています。SSLMate
[Certificate Search API v1](https://sslmate.com/help/reference/ct_search_api_v1)
を毎時37分にポーリングします。外形監視の設定・判定・スケジュールは従来どおりです。

### 初期設定と初期化

1. `ct-targets.json` の `domain` と `include_subdomains` を編集します。Punycodeのドメイン名を使います。`true` は任意の深さのサブドメインを含めます。ワイルドカード証明書も検索します。
2. SSLMateの無料SmallプランでAPIキーを作り、Actions Secretsへ `CERTSPOTTER_API_KEY` を登録します。Slackは既存の `NOTIFY_SLACK_TOKEN` / `NOTIFY_SLACK_CHANNEL_ID` を使います。
3. デフォルトブランチに反映後、Actions → **CT certificate watch → Run workflow** で **initialize** を有効にして一度実行します。
4. レート制限などで一度に完了しなければ、取得済みページを `ct-state` ブランチの `ct-state.json` に保存して終了します。次回の定期実行はinitializeを無効にしたままで途中から初期化を継続します。全ページ取得後にベースラインが確定し、以降は通常監視へ移ります。初期化中の既存発行は通知しません。

初期化は全ページの取得と空配列の確認が必須です。APIが提供するのは既知の**未失効期限の証明書**であり、期限切れを含む全履歴ではありません。初期化の途中失敗ではベースラインを確定しません。取得済みの発行情報とページング位置を `pending` に保存し、次回はその位置から再開します。既存状態があってもinitializeを明示すると全対象を再ベースライン化するため、その間の発行は通知されません。対象追加や `include_subdomains` の変更も明示的な再初期化が必要です。

### 差分・通知・障害

状態はドメインごとの不透明な発行 `id` を `after` として保存します。時刻、NotBefore、期限、フィンガープリントでは差分判定しません。空の初期検索結果も有効なベースラインであり、カーソルは空文字列になります。全対象・全ページの取得後、そのドメインで初めて見る発行元の証明書だけを1回のSlackメッセージにまとめます。対象、発行ID、SAN/CN、CA、RSA/ECDSA等の公開鍵情報、NotBefore、期限、証明書またはprecertificateのSHA-256を含みます。NotBeforeはCAが前後させることがあるため、厳密な実発行時刻ではありません。外部データの `&<>` はエスケープします。発行元はAPIの `issuer.friendly_name`（通知のCA名）の完全一致でドメインごとに判定します。既知の発行元の更新では通知せず、カーソルだけ進めます。同じ会社でもCA名が変われば新しい発行元として通知します。通知成功後に発行元を記録し、以後は通知しません。初期化では既存証明書の発行元を通知せず登録します。旧形式（version 1）の状態は更新後の初回に既存証明書を再取得し、通知せず発行元履歴を作成します。移行中も途中再開でき、完了後はversion 2になります。APIで取得できない期限切れ証明書の発行元は復元できず、移行中に見つかった発行元も既知として登録されます。

処理済みカーソル（`domains`）は全ページ取得・Slack通知成功後だけ更新します。取得途中のページング位置と発行情報（`pending`）は別に保持します。取得失敗、ページング異常、429、JSON不正、タイムアウト、Slack失敗、状態保存・push失敗はいずれも実行失敗です。無料枠による中断も未完了として非ゼロ終了しますが、workflowはチェックポイントを保存し、次回に再開します。取得済みページは再取得せず、Slack失敗時は全件取得済みのチェックポイントから通知だけ再試行します。大きすぎるSlackメッセージも省略せず失敗させます。状態更新競合はActionsの共通concurrencyグループで直列化し、pushも通常のfast-forwardのみです。SlackとGitには分散トランザクションがないため、通知成功後のpush失敗・強制終了では次回に重複通知する可能性があります。発行IDで確認してください。

全件取得に成功し、新規発行も未完了データもなければコミットしません。中断時は再開用の `pending` を保存するためコミットする場合があります。リクエスト回数と次回取得可能時刻は独立したActions artifact（`ct-runtime`、保持90日）で引き継ぎ、通常の空振り取得では状態ブランチを更新しません。最終成功の検知は状態ファイルの更新時刻に依存せず、独立した **CT acquisition health** が毎時53分にActions APIの成功履歴を確認し、24時間成功がない場合に失敗します。GitHub Actionsの失敗通知を有効にし、初期設定後はhealthの手動実行も確認してください。CT関連のSlack投稿は新規発行のみに限定しています。スケジュール自体の停止やGitHubの障害には別途実行履歴の確認が必要です。

### 状態復旧

通常実行でブランチ・ファイルがない場合や不正な場合はエラーとし、自動初期化しません。監視を停止したうえで `ct-state` の履歴・バックアップから直近の正しいJSONを復元し、同ブランチにコミットしてから通常実行してください。`pending` がある場合は同じJSON内の取得済み情報もまとめて復元してください。対象設定も当時のものに合わせます。途中で対象が変わると混在を防ぐため再開を拒否します。古いカーソルに戻すと通知が再送される可能性があります。外部から状態ブランチを書き換える際は実行中ジョブがないことを確認してください。

復元できない場合だけ、見逃しの可能性を確認してinitializeで新しいベースラインを明示作成します。ブランチはあるのにファイルが欠落した場合は、まず履歴から復元するか、実行停止中に状態ブランチを削除してから明示初期化してください。壊れた既存ブランチを自動修復しません。長期停止すると期限切れ証明書はAPI検索対象から外れるため、完全な履歴回収を保証できません。

### Smallプランの制限

[公式プラン表](https://sslmate.com/ct_search_api/)ではSmallは無料、単一ホスト100クエリ/時、サブドメイン込み10クエリ/時、75クエリ/分、5クエリ/秒です（負荷時は低下することがあります）。空ページ・ページング・再試行もリクエストを消費します。同じAPIキーを他の用途と共用しないでください。

通常のリクエスト間隔は約1秒です。直近1時間のリクエストをartifactで引き継ぎ、全体90回・そのうちサブドメイン込み9回を上限に、枠が尽きたら長く待たずに中断します。空ページでは即座に取得完了とし、`Retry-After`（秒またはHTTP日時）は次回の取得前に確認します。429も次回へ延期します。5xx・通信失敗には最大4回の指数バックオフを使いますが、1回の待機が5秒を超える場合は中断します。次回もまだ待機期限内ならAPIを呼ばず終了します。リクエスト回数には空ページ・エラー・再試行も含めます。1リクエスト30秒、取得処理全体4分、workflow全体10分の上限があります。処理時間の上限でも取得済みページを保存して次回へ回します。artifactの取得・解析に失敗した場合はAPIを呼ばずエラーにします。

制限やAPI側の検索タイムアウトにより最後まで取得できない場合、途中の発行を捨てたり、成功扱いしたりしません。処理済みカーソルを保持し、取得済みページを保存して次回に継続します。初期化を含めて全ページが揃うまで通知・ベースライン確定は行いません。1バッチの取得上限1000ページやSlackのメッセージ上限で進めない場合は、対象の分割や状態の明示的な復旧が必要です。

`contents: write` はCT監視ジョブだけに付与します。CT状態ブランチへのpushではテストworkflowを起動しません。状態ブランチにはJSONだけを保存し、Secretsは保存しません。外部APIをモックしたテストはページング、初期化失敗、カーソル維持、通知失敗、429、タイムアウト、エスケープ等を検証します。
